# PR titles and descriptions for a stack

## Title

Descriptive, completes the sentence "This commit ...", names the affected package or component,
includes the ticket when there is one. Canva's common formats:

- `[JIRA-999] <description>`
- `<package>: <description> [JIRA-999]`

Good:

- `[PUB-212] Adds ScheduledPublish proto and regenerated bindings`
- `publish/server: adds SchedulerStore with DynamoDB implementation [PUB-212]`

Bad: `wip`, `part 2`, `update proto`, `more changes`. A reviewer scanning their queue should know
what the PR does from the title alone.

Do **not** put "(1/5)" style counters in the title. Stack order changes when layers are folded or
inserted, and the PR Train block at the end of the body already shows position.

## Body template

Start every PR body from `assets/pr-template.md` (copy it, keep its headings and order) and fill
it in for that layer only. Do not hand-write a stack list: the PR Train block (below) is
generated by `scripts/generate_pr_train_toc.sh` and appended once the PR numbers exist.

How to fill each section:

- **Overview.** Two or three sentences: what this layer changes and why it exists as its own PR.
  Say what it builds on from lower layers and what is intentionally unused until a higher layer,
  so the reviewer does not ask for things that live elsewhere in the stack. If this PR cannot
  merge without another PR in the stack, say so here in one sentence naming the other PR.
- **Related Issue.** The Jira ticket as `[CA-1337](https://canvadev.atlassian.net/browse/CA-1337)`.
  Same ticket on every PR in the stack. If there is no ticket, remove the bullet rather than
  leaving the placeholder.
- **Type of Change.** Tick exactly one box with `[x]`, chosen for *this layer*, not the feature
  overall. A refactor-only PR at the bottom of a feature stack is `Refactor`, not `New feature`.
- **UX Solution** or **Bugged Behaviour**, never both. Keep UX Solution when the stack adds new
  behaviour and delete the Bugged Behaviour section; keep Bugged Behaviour (with Expected and
  Actual filled in) when the stack fixes a bug and delete UX Solution. For a layer with no
  user-visible effect (helpers, schema, wiring), keep the section the stack as a whole uses and
  write one line pointing to the layer where the behaviour becomes visible.
- **Technical Solution.** The reviewer's guide to the diff: what changed, the shape chosen and
  why, anything they might question (a public API choice, a new dependency, a deliberately
  temporary shim). End with what was run at this layer: targeted tests, typecheck, lint. Be
  exact, and say so if the full suite was not run. If a notable share of the lines is generated,
  say how many and where.
- **Before vs After.** Leave the heading and its comment exactly as they are. The author adds the
  media personally.

Remove the HTML comments from sections you have filled in; leave the one under Before vs After.

## The PR Train block

Every PR in the stack ends with this block, generated by `scripts/generate_pr_train_toc.sh`. It is the
same format Canva's `pr-train` tool produces, so reviewers recognise it:

```markdown
<pr-train-toc>

### 🚂 PR Train 
1. #1103425  
1. #1103427  👈
1. #1103428  
<!-- { "pr_train_prs": ["1103425","1103427","1103428"] } -->
</pr-train-toc>
```

Reviewers often open a PR from a notification without seeing GitHub's stack view. The train
shows them where this PR sits and what it builds on, which prevents the two most common
confusions: reviewing the cumulative diff against trunk, and asking for things that live in a
lower layer. The HTML comment carries the PR list, so when the stack changes you can read the
old train from any one PR before writing the new block.

The script only prints the block. With no arguments it reads the current `gh stack`, looks up
each branch's PR number, and puts 👈 on the checked-out branch's PR. Putting the block into a
description is a manual three-step swap, repeated on each branch of the stack:

```bash
scripts/generate_pr_train_toc.sh                                    # block for the current branch's PR
gh pr view --json body -q .body > body.md                           # always the latest body from GitHub
# edit body.md: remove any existing <pr-train-toc>...</pr-train-toc> block (wherever it is),
#               then append the printed block as the last thing in the file
gh pr edit --body-file body.md
```

When the stack is not checked out locally, pass the ids explicitly:

```bash
scripts/generate_pr_train_toc.sh --current 1103427 1103425 1103427 1103428   # PRs bottom to top
```

Rules for the swap: exactly one block per description, always at the very end, and never leave
a stale one behind. Fetch the body fresh each time rather than reusing a file you wrote
earlier, so changes made in the browser survive.

## Filling the template non-interactively

Write each body to a temp file and apply it:

```bash
gh pr edit <branch> --title "<title>" --body-file /path/to/body.md
```

PR numbers are only known after `gh stack submit`, so write bodies afterwards. Get them with
`gh pr view <branch> --json number,url,title`.
